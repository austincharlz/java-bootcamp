## JPA Readiness Notes

**Future lab (Lab 26+):**

- Replace `InMemoryCustomerRepository` implementation with `extends JpaRepository<Customer, String>`.
- Add `@Entity` and `@Id` to `Customer` model (or keep as is if using name-based mapping).
- Add `spring-boot-starter-data-jpa` and a database starter (PostgreSQL, H2, etc.) to `pom.xml`.
- **No changes needed** to `CustomerService`, `CustomerController`, or any route — they only call `CustomerRepository` interface.
- Routes like `POST /api/customers` and `GET /api/customers/{id}` stay unchanged because the controller and service never import a concrete repository class.

This seam is the payoff of layering: **swapping storage from in-memory to JPA is a single-class change** (`InMemoryCustomerRepository` → `JpaRepository`), and the business rules in `CustomerService` and HTTP mappings in `CustomerController` are untouched.

## Layering Validation

✓ Controller depends only on `CustomerService` (no repository imports).  
✓ Service owns business rules (duplicate checks) and depends on `CustomerRepository` interface.  
✓ Repository interface is persistence-agnostic (no JPA annotations).  
✓ In-memory implementation is pluggable and seeded for testing.  
✓ Both HTTP and SOAP endpoints (if extended) can call the same `CustomerService`.
